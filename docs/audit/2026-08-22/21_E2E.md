## BI — Browser E2E — NOT TESTED (no harness exists)

There is **no Playwright, Puppeteer, Cypress or Selenium setup** in the repository. The
plan's target scenario —

```
launch server → browser → configure virtual instrument → import MIDI
→ assign → adapt → play → edit → save → reload → verify
```

— cannot be run today.

This is the **single largest structural gap in the test strategy**, and it is the
prerequisite for a long list of other sections that are currently unanswerable:
§Q01 (piano-roll drag/resize/select), §AM (UI inventory), §AN (UX journeys),
§AO (responsive), §AR (accessibility), §AU/§AV (frontend performance and memory),
§AI's automated XSS payloads.

**Conditions are unusually favourable for adding one.** Chromium is already available in
typical CI images, the server boots headlessly in seconds with no hardware, virtual
instruments remove the need for real MIDI devices, and the WebSocket contract is stable
and correlated by `id`. A first E2E suite covering the scenario above is a few hundred
lines, and it would convert roughly seven currently-unanswerable sections into testable
ones. Highest leverage-per-effort item in this audit.

## BW — Global coherence — PARTIAL

The plan's chain:

```
UI → WebSocket → Command → Service → Database/MIDI → Transport → real instrument → UI feedback
```

**Verified in this audit (level 3, no hardware):**

```
WS client → {id, command, data}
  → CommandRegistry envelope validation      ✔  (ERR_VALIDATION on bad shape)
  → JsonValidator.validateByCommand          ⚠  fails open for 184/270 commands (F-03)
  → versioned handler lookup                 ✔  (ERR_NOT_FOUND on unknown command)
  → async handler → service → Database       ✔  (device_list round-trips)
  → {id, type:'response', data, duration}    ✔  correlated by id
```

The backend half of the chain is coherent and behaves exactly as documented. Broadcast
events (`type:'event'`) are correctly distinguished from correlated responses.

**Not verified:** the two ends. `UI → WebSocket` needs a browser (§BI);
`Transport → real instrument → UI feedback` needs hardware (§BJ). So the chain is proven
in the middle and unproven at both extremities — which is precisely the shape the plan
warns about when it says a static audit is insufficient for this project.
